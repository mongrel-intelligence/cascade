### Assumed decisions (autonomous run — Phase 3/4 sign-off gates stated, not asked)

The operator ran this planning pass unattended, so the decomposition and interview decisions below were taken on the recommended option and are recorded here for audit. Any of them can be overturned by editing the plan files in place before `/implement`.

1. **Three serial plans, not one.** Seams: shared evaluation model (1) → evidence producers and `session finish` (2) → profile opt-in, e2e proof, docs (3). Each is reviewable alone and leaves every agent's behaviour unchanged until 3. A single plan would put the fail-closed evaluator, CLI plumbing across nine files, and prompt changes in one review.
2. **Alternatives are expressed as `scm.pushedChangesAlternatives: [pr-response]` next to `requiresPushedChanges: true`.** The existing flag keeps driving sidecar creation, git-state stop hooks and env plumbing; only the evaluation points learn about the OR-group. A load-time refinement rejects the flag without `requiresPushedChanges: true`, so no agent can inherit the alternative implicitly (spec AC #8, strategic decisions 1 and 4). Rejected: a top-level `anyOf` group replacing the boolean flags — it would have forced every `requiresPushedChanges` consumer to re-derive "may need push evidence".
3. **"Substantive response" = a successful new top-level PR comment or inline review reply**, recorded by the two posting tools; content is not judged, and `update-pr-comment` never records (spec strategic decision 2, AC #4).
4. **Repository state is re-checked worker-side**, not trusted from the CLI: `readCompletionEvidence` runs `git status --porcelain` and `git rev-parse HEAD` in `repoDir` and compares against `initialHeadSha`; `session finish` applies the same rule so the agent gets the rejection immediately. Any git failure or missing SHA fails the alternative closed (spec strategic decision 6).
5. **`initialHeadSha` is `input.headSha`** (the PR head at dispatch, already exported to the CLI as `CASCADE_INITIAL_HEAD_SHA`) rather than a fresh `git rev-parse HEAD` at run start, so both sides compare against the same SHA and no new "must have new commits" rule appears for PM-triggered runs.
6. **In-process gadgets (`PostPRComment`, `ReplyToReviewComment`) record the response in session state** so the SDK engine's `Finish` gadget behaves like `cascade-tools session finish`; the spec's engine-parity AC names native-tool engines, and this costs two lines.
7. **`pushed-changes` wins when both branches are satisfied** (a push is the more authoritative outcome), and the pushed-changes sidecar is written only for that outcome.
8. **`postProcessResult` consumes the shared evaluator** instead of keeping its own pushed-changes verdict, so the adapter and the continuation loop cannot drift (spec AC #7).
9. **Architecture docs land in plan 3**, once an agent actually exhibits the behaviour; plans 1 and 2 add CHANGELOG blocks only.
10. **Test distribution:** each test lives in the plan that delivers the code under test; the end-to-end suite lives in plan 3 because only then does the real profile exercise the chain.
